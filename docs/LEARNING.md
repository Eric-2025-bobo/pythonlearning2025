# 从读懂代码到独立维护作品

## 第一周：跑通并解释

1. 在单独的 demo.db 中走一遍 README 的完整命令流程。
2. 从 models.py 开始读：理解 dataclass、类型注解和异常。
3. 读 storage.py：把每个 SQL 对应到新增、查询、更新、删除；解释事务和参数绑定。
4. 读 service.py：理解为什么校验在写入之前。自己画出 add 命令的调用顺序。
5. 读 cli.py：解释 argparse、分支分发、stderr 和退出码。
6. 读 tests/test_tasks.py：理解 fixture、tmp_path、parametrize；改坏日期校验，观察测试失败，再修复。
7. 不看原实现重新写一个 show 命令，并用测试确认。

请能回答：为什么默认数据不放仓库？为什么不直接拼接用户输入到 SQL？
为什么 due=None 与“不修改 due”不同？为什么测试数据库需要隔离？

## 第二周：独立实现截止日期筛选

目标：新增 list --overdue，仅返回未完成且截止日期早于今天的任务。
先写测试：昨天、今天、明天、无日期、已完成任务分别应如何处理。
不要把当前时间藏在数据库内：让服务接收可注入的 today，方便确定性测试。
随后修改 CLI 和 README，并通过 feature/overdue 分支提交 PR。

## 后续迭代与验收

| 版本 | 功能 | 验收 |
| --- | --- | --- |
| 0.2 | 逾期筛选、统计 | 日期边界测试，真实使用一周 |
| 0.3 | 标签和数据库迁移 | 老数据库升级后旧任务仍完整，迁移失败可恢复 |
| 0.4 | JSON/CSV 导入导出 | Unicode、重复记录、损坏文件测试；导入事务化 |
| 0.5 | FastAPI 接口 | 复用业务层、API 测试、明确鉴权和数据边界 |
| 1.0 | 发布与展示 | 打包安装验证、演示视频、发布说明、设计文档 |

每次只选一项：提出问题 → 写验收条件 → 功能分支 → 实现和测试 → PR → 回顾。
避免一开始同时加入爬虫、AI、网页和云服务。

## 让它成为可信的简历作品

积累自己的提交、Issue、PR、设计取舍、修复过程和实际使用反馈。
记录可验证的数据，如测试数量、支持命令、平台验证结果；不要虚构用户数、性能或独立开发贡献。
准备一个两分钟演示：创建任务 → 检索 → 完成 → 重启后数据仍在 → 执行测试。
能够现场解释事务、参数绑定、分层、异常边界，比堆砌框架更有价值。
